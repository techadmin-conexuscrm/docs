# Calls: indexes for the campaign dialer's per-number checks; real-Postgres tests in CI

**Base:** `main` · **Migration:** `0111` · **Merge order:** 1 of 14

## Problem
The campaign dialer, which comes in the PRs stacked on this one, checks two things for every lead it considers:
- how many times this customer or number was called in the last 24 hours (the cap);
- whether the agent is on a live call.

On `calls` as it stands, both checks are sequential scans of the company's whole call history.

The repository also had no way to run tests against real Postgres. Locking, unique indexes, CHECKs and triggers could only be tested against a fake.

## Root cause
- `calls` has no index matching `(organization_id, customer_id, created_at)` or `(organization_id, to_number, created_at)`, and none for "this user's live calls".
- The vitest setup had only the `unit` project.

## Fix
- **Migration 0111** adds three plain indexes on `calls`:
  - `calls_org_customer_created_idx`;
  - `calls_org_to_number_created_idx`;
  - `calls_user_live_idx`, partial: `status IN ('initiated','ongoing')`.
- **A `db` vitest project** (`*.db.test.ts`) runs against a real database from `TEST_DATABASE_URL`, using `src/test-utils/real-db*.ts`. The CI workflow starts Postgres for it. `npm run test:db` runs it alone.

## Why this is safe
- No application behaviour changes. Nothing reads the new indexes until the dialer ships, and the old code ignores them.
- The migration starts with `SET LOCAL lock_timeout = '10s'`, and it uses plain `CREATE INDEX` (never `CONCURRENTLY`, since drizzle runs the batch in one transaction).
- The build blocks **writes** to `calls` while it runs. That happens inside the deploy restart, when the API is already down. Reads are not blocked.
- **Deploy-time cost:** the restart (30–60 s) plus the index build, which grows with the number of rows in `calls`. Check `select count(*) from calls` before choosing the window.
- Rollback: revert the code. The indexes are harmless to the old code.
- **This PR is Deploy 1 on its own,** so the one migration that locks a large live table is isolated.

## Test plan
- **Gates** (this head): `npx tsc --noEmit`; full `npx vitest run` (unit + real-Postgres `db` project); scratch migrate from empty then `npx drizzle-kit generate` → "No schema changes".
- After deploy:
  - login returns 401 for bad credentials;
  - `/api/v1/health` is green;
  - `\d calls` lists the three indexes;
  - one manual test call places and ends normally.
